Example · Randomness

Security starts with unpredictable randomness.

Use crypto/rand for keys, nonces, reset links, and session tokens. Never use math/rand for secrets.

package main

import (
    "crypto/rand"
    "encoding/hex"
)

func newToken() (string, error) {
    b := make([]byte, 32)
    if _, err := rand.Read(b); err != nil {
        return "", err
    }
    return hex.EncodeToString(b), nil
}

Go · Encrypt

Prefix the random nonce to the sealed output.

nonce12 bytes
ciphertextencrypted data
tag16 bytes

AES keys must be 16, 24, or 32 bytes. Prefer a random 32-byte key for AES-256.

func encrypt(plain, key, aad []byte) ([]byte, error) {
    block, err := aes.NewCipher(key)
    if err != nil { return nil, err }
    aead, err := cipher.NewGCM(block)
    if err != nil { return nil, err }

    nonce := make([]byte, aead.NonceSize())
    if _, err := rand.Read(nonce); err != nil {
        return nil, err
    }
    return aead.Seal(nonce, nonce, plain, aad), nil
}
Seal16
Go · Decrypt

Open verifies before returning plaintext.

A wrong key, nonce, associated data value, ciphertext byte, or tag produces an error.

!

Treat failure as untrusted input.

Do not return partial plaintext, reveal which check failed, or retry with weaker settings.

func decrypt(blob, key, aad []byte) ([]byte, error) {
    block, err := aes.NewCipher(key)
    if err != nil { return nil, err }
    aead, err := cipher.NewGCM(block)
    if err != nil { return nil, err }

    n := aead.NonceSize()
    if len(blob) < n+aead.Overhead() {
        return nil, errors.New("invalid ciphertext")
    }
    nonce, sealed := blob[:n], blob[n:]
    return aead.Open(nil, nonce, sealed, aad)
}

Deep dive · Public-key cryptography

Two related keys separate public operations from private ones.

The same key-pair idea supports encryption, digital signatures, and key agreement—but each job uses a different construction.

Asymmetric cryptography22
The key-pair model

Share one key. Protect the other.

Public key

Distribute it widely. Other people use it to encrypt to you or verify your signature.

safe to publish ⌁

Private key

Keep it secret. You use it to decrypt, sign, or derive a shared secret.

protect like a production credential ⚿

The keys are mathematically related, but deriving the private key from the public key should be computationally infeasible.

Key pair23
Do not mix the operations

“Public-key crypto” is a family of different guarantees.

Encrypt a small secret

Public key encrypts; private key decrypts. Example: RSA-OAEP wrapping a data key.

01

Sign a message

Private key signs; public key verifies. Example: Ed25519 software-release signatures.

02

Agree on a key

Two key pairs derive the same secret. Example: X25519 followed by HKDF.

RSA is not bulk-data encryption.

The trust problem

A key is useful only when you know whose key it is.

Certificates, pinned keys, fingerprints, and trusted directories bind a public key to an expected identity.

Trusted issuerSigns binding
→
CertificateIdentity + public key
→
VerifierChecks chain + name + time
?

An attacker can publish a perfectly valid key pair.

The security question is not “does this key work?” but “is this the authentic key for the identity I intended?”

Certificates and trust33
Before shipping

Use high-level constructions and protect private operations.

  1. Use RSA-OAEP, not PKCS #1 v1.5 encryption.
  2. Encrypt bulk data with AEAD and wrap only its key.
  3. Use Ed25519 or an established signature protocol.
  4. Run ECDH output through HKDF before use.
  5. Authenticate every public key you accept.
  6. Keep private keys in a KMS, HSM, or restricted store.
  7. Version keys and plan rotation or revocation.
  8. Prefer TLS, HPKE, or another reviewed protocol.

Use PKCS #8 for portable private-key encoding and PKIX SubjectPublicKeyInfo for public keys; PEM is only the textual container.

Deep dive · Secure transport

TLS turns public-key trust into fast, authenticated traffic.

TLS and X.50935
Security boundary

TLS protects a connection—not the whole application.

What TLS provides

  • Confidentiality for application bytes in transit
  • Integrity and tamper detection
  • Server identity through certificate validation
  • Optional client identity with mutual TLS

What TLS does not provide

  • Application authorization or safe business logic
  • Protection after either endpoint is compromised
  • Encryption for data after it is stored
  • Complete hiding of connection metadata

Key format map44
Go · Public keys

Generic PKIX keys return a concrete key type.

  • PUBLIC KEY may contain RSA, ECDSA, Ed25519, or ECDH
  • RSA PUBLIC KEY contains PKCS #1 RSA only
  • A certificate’s PublicKey is already parsed
block, _ := pem.Decode(publicPEM)
if block == nil { return nil, errNoPEM }

switch block.Type {
case "PUBLIC KEY":
    return x509.ParsePKIXPublicKey(block.Bytes)
case "RSA PUBLIC KEY":
    return x509.ParsePKCS1PublicKey(block.Bytes)
case "CERTIFICATE":
    cert, err := x509.ParseCertificate(block.Bytes)
    if err != nil { return nil, err }
    return cert.PublicKey, nil
default:
    return nil, fmt.Errorf("unexpected %q", block.Type)
}

Key serialization48
Before shipping

Parsing successfully does not mean trusting safely.

  1. Keep normal TLS certificate verification enabled.
  2. Validate DNS names through SAN—not Common Name.
  3. Send the leaf certificate and intermediate chain.
  4. Use system roots or a deliberately scoped private pool.
  5. Match the PEM label to the exact DER parser.
  6. Prefer PKIX public keys and PKCS #8 private keys.
  7. Reject unexpected algorithms, usages, and key sizes.
  8. Store private keys in a KMS/HSM when possible.

Go’s PKCS #8 parser handles unencrypted keys. Legacy x509.DecryptPEMBlock is deprecated because its RFC 1423 encryption is unauthenticated; use a KMS or a reviewed encrypted-key workflow.

Deep dive · Hashing

A small fingerprint for any amount of data.

Hashing is one-way, deterministic, and sensitive to every input bit. Those properties make it a versatile building block—not encryption.

crypto/hmac57
HMAC · Security boundary

HMAC proves that the sender knew the shared key.

What it provides

  • Integrity: changed bytes fail verification
  • Authenticity: the tag requires the secret key
  • Fast authentication for messages and API requests

What it does not provide

  • Confidentiality: the message remains readable
  • Replay protection: a valid message can be resent
  • Non-repudiation: either key holder can create a tag
≠

HMAC is not encryption and not a digital signature.

It authenticates possession of a shared secret. It does not identify which holder created the message.

HMAC · Under the hood

HMAC hashes twice with two key-derived pads.

1 · Inner hashinner = H((K′ ⊕ ipad) ∥ message)
2 · Outer hashtag = H((K′ ⊕ opad) ∥ inner)
→

The inner and outer pads separate the two hash operations. Use the standard construction—never invent hash(key || message).

K′ is the key normalized to the hash block size; ∥ means concatenation.

HMAC · Before shipping

Most HMAC failures happen around the primitive.

  1. Generate keys with crypto/rand.
  2. Use at least 32 random bytes for HMAC-SHA-256.
  3. Use a separate key for each purpose and trust boundary.
  4. Version keys so they can be rotated safely.
  5. Compare tags with hmac.Equal.
  6. Authenticate every field that affects behavior.
  7. Add timestamps and nonces when replay matters.
  8. Never log keys or include them in source code.

Transmit a key identifier with the message when receivers need to select among active rotation keys. The identifier is not secret.

Go · Login verification

Recompute using stored parameters, then compare in constant time.

  • Parse and validate the PHC string
  • Reject unsupported versions and excessive costs
  • Derive the candidate digest

func verifyPassword(stored string, password []byte) (bool, error) {
    p, salt, expected, err := decodePHC(stored)
    if err != nil || !allowed(p) {
        return false, errors.New("invalid verifier")
    }
    got := argon2.IDKey(password, salt,
        p.time, p.memory, p.threads, uint32(len(expected)))

    ok := subtle.ConstantTimeCompare(got, expected) == 1
    return ok, nil
}

Before shipping

A strong hash is one layer of the authentication system.

  1. Allow long passphrases; cap unreasonable request sizes.
  2. Rate-limit login attempts by account and network signals.
  3. Return the same public error for unknown users and bad passwords.
  4. Perform comparable work for nonexistent accounts.
  5. Benchmark cost under peak authentication concurrency.
  6. Store algorithm and parameters with every verifier.
  7. Rehash after successful login when policy changes.
  8. Add MFA and protect password-reset flows.
!

Never log passwords, derived digests, or pepper values.

Use byte slices carefully, limit secret exposure, and keep any pepper in a dedicated secret store—not beside the verifier database.

Password checklist73
Decision guide

“Hash it” is not a complete design.

Start with the guarantee you need, then choose the construction.

  • Detect changesSHA-256 or SHA-3, plus a trusted expected digest
  • AuthenticateHMAC-SHA-256 with a strong secret key
  • Store passwordsArgon2id, scrypt, or bcrypt—salted and costly
  • Sign dataA digital-signature API such as Ed25519
×

Do not choose MD5 or SHA-1 for security.

They remain available for legacy compatibility, but collision attacks make them unsuitable for secure applications.

Hashing choices74
Before shipping

Make the secure path the boring path.

  1. Define the exact security goal and threat.
  2. Use crypto/rand for secret randomness.
  3. Prefer TLS and AEAD over hand-built schemes.
  4. Let the library generate or validate nonces.
  5. Keep keys outside code; plan rotation.
  6. Use dedicated password hashing—not a fast hash.
  7. Keep Go patched and scan dependencies.
  8. Test failures: wrong key, changed data, bad cert.

Password hashing algorithms such as Argon2 and bcrypt live in golang.org/x/crypto, not the standard library.

Practice75
Final section · Defensive review

Cryptographic failures usually happen around the algorithm.

The primitive may be strong while randomness, nonces, trust, key storage, message formats, or error handling quietly remove the guarantee.

Common mistakes76
Mistake 01 · Predictable secrets

Random-looking is not cryptographically unpredictable.

Avoid

  • math/rand for keys, tokens, salts, or nonces
  • Time-based seeds and UUIDs as encryption keys
  • Hardcoded secrets or human-readable key strings
  • Using a password directly as an AES key

Prefer

  • crypto/rand or a managed KMS
  • Algorithm-sized uniformly random keys
  • Argon2id or another KDF for password-derived keys
  • Explicit error handling during key generation
wrong: key := []byte("my-secret-key")
right: key := make([]byte, 32); _, err := rand.Read(key)
Secure randomness77
Mistake 02 · Designing a custom scheme

A secure primitive does not make a secure protocol.

Composition determines whether confidentiality, integrity, identity, ordering, and replay guarantees survive.

AES aloneUse an AEAD mode such as AES-GCM—not raw blocks or ECB.
CTR / CBC aloneEncryption without authentication permits undetected changes.
hash(key || msg)Use HMAC instead of inventing keyed hashing.
custom handshakeUse TLS, HPKE, or another reviewed protocol.
↑

Raise the abstraction level.

Prefer APIs that implement the complete security property: HTTPS, AEAD, HMAC, Ed25519, password-hashing libraries, and envelope encryption.

Mistake 04 · Unsafe password storage

Passwords should be verified—not decrypted.

Avoid

  • Plaintext or reversibly encrypted passwords
  • MD5, SHA-1, or SHA-256 password hashes
  • One global salt or no salt
  • Unbounded Argon2 parameters from stored input
  • Ignoring bcrypt’s 72-byte input limit

Prefer

  • Argon2id for new systems
  • A unique random salt per password
  • Algorithm and cost stored with the verifier
  • Benchmarking under peak concurrency
  • Rehashing after login when policy changes

An optional pepper belongs in a separate secret store. It is not a replacement for salt, work factors, rate limits, or MFA.

Mistake 06 · Weak key lifecycle

Keys require ownership from creation through destruction.

The algorithm cannot protect a key copied into Git, logs, crash reports, broad configuration, or an unrestricted database.

  1. Generate keys inside a KMS/HSM when possible.
  2. Separate keys by environment, tenant, and purpose.
  3. Grant decrypt/sign access only to required identities.
  4. Store a non-secret key ID beside ciphertext.
  5. Rotate while retaining controlled old-key access.
  6. Audit key use and alert on unusual operations.
×

Deleting a key can permanently destroy encrypted data.

Rotation, revocation, archival retention, backup, and destruction need an explicit recovery-aware policy.

Final review

Review the complete guarantee—not only the algorithm name.

  1. Is the threat and required property explicit?
  2. Is a reviewed protocol or high-level API available?
  3. Are keys, salts, and tokens generated securely?
  4. Are keys scoped, stored, versioned, and rotatable?
  5. Does encryption authenticate data and context?
  6. Can a nonce ever repeat under the same key?
  7. Are peer identities and certificate chains verified?
  8. Are replay, ordering, and canonicalization handled?
  9. Do negative tests alter every protected component?
  10. Are Go, dependencies, and vulnerability scans current?

Avoid: custom crypto · disabled verification · hardcoded keys · ignored errors
